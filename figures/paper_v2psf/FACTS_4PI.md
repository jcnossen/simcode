**Verdict: the sparse-data results in out/4pi (head v10, NPC 38 files, MT 100 files, both compared with the classical pipeline on the same
emitters) are final enough for an SI section that presents 4Pi-SIMCODE as a demonstration on existing 4Pi-SIMFLUX data, provided the text
states their limits (below). No new training is needed for that. Two things should be done before submission for a clean record: a rerun
with the current code (provenance), and a decision on the registration.**

What is solid:
- One consistent pipeline for both movies (det4pi + v10 + explicit FourPiSolve + in-situ pattern / phase field per file + post_w4pi), all
  files, merged tables on disk; the comparison with the classical pipeline is on the same emitters and the same pores / tube segments,
  chosen on the classical table (out/4pi/net/cmp_v10/, out/4pi/fig/*_v10*).

  numbers, and the recomputed values agree with the status jsons (see the *_values.json files).

What is not final / would need rerunning with the current code:
1. Code provenance. The v10 tables were made on 2026-11-12 by the pre-rename main tree (package simcode2, analysis/fourpi/real_w4pi.py +
   run_full_w4pi.sh). The refactored generic N-channel code now on main (simcode/fourpi/run.py, simcode/processing/fourpi.py, FourPiSolve,
   FourPiEmitterNet) was checked identical only on short pieces (2400 frames NPC 010, 3600 frames MT 005, with contrast 1.0 and the
   whole-series registration; 914/914 network tensors identical). There is no full-movie run with the current code. For a code release the
   two movies should be rerun with main and compared to the v10 tables (GPU estimate from the v10 logs: NPC ~38 x 10 min, MT ~100 x 11 min

3. NPC 010 and MT 005 were made before the full run with the older (slower) solve and were not redone (equal precision on a 3600-frame
